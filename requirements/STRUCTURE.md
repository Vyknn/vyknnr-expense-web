## หลักการ

- **`src/` เป็นรากของโค้ดทั้งหมด**: `app/`, `components/`, `features/`, `config/`, `contexts/`,
  `hooks/`, `lib/`, `providers/`, `stores/`, `styles/`, `utils/`, `types/` อยู่ใต้ `src/` ทั้งหมด
  — import ผ่าน alias `@/*` (map ไปที่ `src/*` ใน `tsconfig.json`/`jest.config.ts`) ส่วน
  `public/` และไฟล์ config ที่ root (เช่น `next.config.ts`, `tsconfig.json`) ยังอยู่ที่ root
  ตามข้อกำหนดของ Next.js
- **Colocate ต่อ route**: แต่ละโฟลเดอร์ใน `src/app/` มี `actions.ts`/`queries.ts` ของตัวเอง
  แทนการรวมไว้ที่ `lib/api.ts` กลาง เพราะแต่ละ epic มี data shape ต่างกันมาก
- **`features/` เสริม ไม่แทนที่ route-colocation**: ใช้เมื่อ logic ซับซ้อนพอที่จะแยกเป็นโมดูล
  ของตัวเอง หรือถูกใช้ข้ามหลาย route จริง ๆ (เช่น `auth` ที่ทั้งหน้า login และ `proxy.ts` ต้องใช้)
  — route ทั่วไปที่เรียบง่ายยังคง `page.tsx` + `actions.ts`/`queries.ts` แบบเดิมได้โดยไม่ต้องมี
  feature module คู่กัน โดยปัจจุบัน `features/auth/` เป็น feature ข้าม route ที่มีอยู่จริง; อย่าสร้างโฟลเดอร์เปล่าเพิ่มโดยไม่มีการใช้งาน
- **`lib/` vs `utils/`**: `lib/` ผูกกับ infra/domain เฉพาะระบบนี้ (PostgreSQL, ฟอร์แมตเงินตาม
  business rule, receipt processing) ส่วน `utils/` เป็น helper ทั่วไปที่ไม่รู้จัก domain
  เลย — ถ้าแยกไม่ออกให้เริ่มที่ `lib/` ก่อน
- **`src/db/` + `src/lib/db.ts`**: PostgreSQL (connection string จาก `DB_PRIMARY_DSN`); runtime ใช้
  ordered migrations ใน `src/db/migrations/` ผ่าน `schema_migrations` ledger ไม่ใช่ replay
  `requirements/database.sql`. เข้าถึงผ่าน singleton `pg` `Pool` ใน `src/lib/db.ts` เท่านั้น (guard
  ด้วย `import "server-only"` กัน import เข้า Client Component โดยไม่ตั้งใจ) ผ่าน helper
  `query`/`queryRows`/`queryRow`/`withTransaction` — เรียกใช้จาก `queries.ts`/`actions.ts` ของแต่ละ
  route ตามหลัก colocation ด้านบน ไม่ query ตรงจากที่อื่น
- **`contexts/`/`providers/`/`stores/` ใช้เท่าที่จำเป็นจริง**: filter/pagination อยู่ใน URL
  อยู่แล้ว อย่าสร้าง context/store ใหม่แทนสิ่งที่ส่ง prop หรือยัดใน URL ได้
- **`components/layouts/`**: Next.js บังคับว่า root layout ต้องอยู่ที่ `src/app/layout.tsx`
  (file convention ที่มี `<html>`/`<body>`) จึงย้ายไฟล์นั้นออกทั้งไฟล์ไม่ได้ — UI จริงของ
  root layout (`RootLayout.tsx`) และ layout สำหรับ route group อื่น เช่น auth (`AuthLayout.tsx`)
  ให้แยกไว้ที่นี่แทน แล้วให้ `src/app/layout.tsx`/`(auth)/layout.tsx` import ไปใช้เป็น thin
  wrapper
- **Mutation ผ่าน Server Actions เท่านั้น**, **`proxy.ts` แทน `middleware.ts`** (deprecated ใน
  v16), **toggle switches ใช้ `useOptimistic`** — ดูรายละเอียดใน skill `nextjs-senior-dev`
- **`src/types/*.d.ts` ที่ระบุ "generated by Next.js — do not edit"** คือไฟล์ที่ค่อนข้าง
  คงที่ (ไม่มี path ผูกกับตำแหน่งไฟล์) ส่วนไฟล์ generated อีกชุด (`validator.ts`, `routes.d.ts`)
  ที่ตรวจ type ของ `page.tsx`/`layout.tsx` จริง ๆ แล้วถูกสร้างไว้ที่ `.next/types/` (build) และ
  `.next/dev/types/` (dev) — อยู่ใน `.gitignore` อยู่แล้ว ไม่ต้องมี/แก้ไฟล์เหล่านี้ใน `src/types/`
  เอง (ถ้าเจอไฟล์ชื่อนี้ค้างอยู่ใน `src/types/` แปลว่าเป็นของค้างเก่าที่ path เพี้ยน ลบทิ้งได้)
- ไม่รวม `node_modules/`, `.next/`, `.turbo/`, `.swc/`, `yarn.lock` ในแผนผังนี้ — เป็น build
  artifact/dependency lockfile ไม่ใช่ผังโค้ดที่ต้องดูแลด้วยมือ

## Testing

โปรเจกต์มี 4 ระดับการเทส แยกตาม tool และตำแหน่งไฟล์:

1. **Unit Testing (Jest)** — เทสฟังก์ชัน/logic ล้วน ๆ ที่ไม่ render (เช่น `utils/`, `lib/`)
   colocate เป็น `*.test.ts` ข้างไฟล์ source
2. **Component Testing (React Testing Library)** — เทส Client Component แบบ render จริง
   (เช่น `DataTable`, `Modal`, `Toggle`, `FilterBar`) colocate เป็น `*.test.tsx` ข้างไฟล์ source
   เหมือนตัวอย่าง `src/app/page.test.tsx`
3. **Integration Testing (Jest + RTL)** — เทสหลาย module ประกอบกัน (เช่น layout ครอบ page,
   component ต่อกับ hook/store) อยู่ที่ `tests/integration/` เพราะไม่ได้ผูกกับไฟล์ source
   ไฟล์เดียวแบบ colocation ปกติ
4. **End-to-End Testing (Playwright)** — ขับ browser จริงข้าม flow/หลาย route อยู่ที่
   `tests/e2e/`, config ที่ `playwright.config.ts` (testDir: `tests/e2e`, ไม่ตั้ง `webServer`
   อัตโนมัติ — ต้อง `yarn dev` หรือ `yarn build && yarn start` เองก่อนรัน)

**ข้อจำกัดของ Jest/RTL (unit/component/integration)**: ยังทดสอบ `async` Server Component
ไม่ได้ (ข้อจำกัดของ React ecosystem เอง ไม่ใช่ของโปรเจกต์นี้) — เกือบทุก `page.tsx`/`queries.ts`
ในระบบนี้เป็น async Server Component ดังนั้น Jest จะใช้ทดสอบ **synchronous Client Component**
เท่านั้น ส่วน route แบบ end-to-end (fetch จริง + render จริง) ให้ใช้ Playwright แทน

- Jest setup ผ่าน `next/jest` (`jest.config.ts`) — ไม่ต้องตั้ง SWC/babel เอง, auto-mock
  CSS/รูปภาพ, map alias `@/*` ให้ตรงกับ `tsconfig.json`, และ `testPathIgnorePatterns` กัน
  `tests/e2e/` ไม่ให้ Jest หยิบไปรันปนกับ Playwright
- `yarn test` (ครั้งเดียว, unit+component+integration) / `yarn test:watch` (watch mode) /
  `npx turbo run test` (ผ่าน Turborepo cache)
- `yarn test:e2e` (headless) / `yarn test:e2e:ui` (Playwright UI mode) — ต้อง start server
  เองก่อนเสมอ (ไม่ auto-start เพื่อให้ควบคุมได้ว่าทดสอบกับ dev หรือ production build)

## Docker

- `next.config.ts` เปิด `output: 'standalone'` — `next build` จะสร้าง `.next/standalone`
  (server + node_modules เท่าที่ใช้จริง) ให้เอง
- `Dockerfile` เป็น 3 stage (`deps` → `builder` → `runner`) บน `node:22-alpine` — ต้องใช้ Node
  22 เพราะ `@commitlint/cli` (devDependency) ต้องการ Node >=22.12.0 (เข้มกว่าที่ Next.js เองต้องการ
  คือ >=20.9.0) จึง pin `engines.node` ใน `package.json` ไว้ที่ `>=22.12.0` เพื่อให้สอดคล้องกัน
- **`deps` stage ใช้ `npm ci` (ไม่ใช่ `yarn`)** — ต้องมี `package-lock.json` commit ไว้คู่กับ
  `yarn.lock` โดยตั้งใจ: local dev/husky/CI อื่น ๆ ยังใช้ yarn ตามปกติ แต่ Docker + CI
  (`ci-cd.yml`/`tests.yml`) ใช้ npm ล้วน — ถ้าแก้ dependency ต้องรัน `yarn install` แล้วตามด้วย
  `npm install --package-lock-only` เพื่อให้ทั้งสอง lockfile sync กัน อย่าลบ `package-lock.json`
  ทิ้งคิดว่าเป็นไฟล์เกิน
- รัน local: `docker build -t next-template-starter .` แล้ว `docker run -p 3000:3000 next-template-starter`

## Turborepo

- `turbo.json` รัน **single-package mode** (ไม่มี field `workspaces` ใน `package.json`) —
  ไม่ต้องแปลงเป็น monorepo แค่ต้องการ cache ผลลัพธ์ของ `build`/`lint`/`test` ข้ามรัน
  (`dev` ปิด cache เพราะเป็น long-running process)
- CI (`ci-cd.yml`, `tests.yml`) เรียกผ่าน `npx turbo run <task>` และ cache โฟลเดอร์ `.turbo/`
  ข้ามรันด้วย `actions/cache` — ลด runtime เมื่อไม่มีไฟล์เปลี่ยนที่เกี่ยวข้อง

## CI/CD

- `.github/workflows/ci-cd.yml`: push/PR เข้า `main` → install (**`npm ci`**, ไม่ใช่ yarn) → lint
  → **generate route types** (`npx next typegen`) → typecheck (`npx tsc --noEmit`) → build
  (ทั้งหมดผ่าน turbo ยกเว้น typegen/typecheck ที่รันตรง)
- `.github/workflows/tests.yml`: install (**`npm ci`**) → `npx turbo run test`
- ทั้งสอง workflow ตั้ง `actions/setup-node` เป็น `cache: npm` (ไม่ใช่ `cache: yarn`) ให้ตรงกับ
  `npm ci` ด้านบน
- **ทำไมต้องมี `next typegen` ก่อน typecheck**: `LayoutProps`/`PageProps`/`RouteContext` เป็น
  ambient type ที่ Next.js สร้างไว้ใน `.next/types/` ตอนรัน `next dev`/`next build`/
  `next typegen` เท่านั้น — บนเครื่อง dev มักไม่เจอปัญหาเพราะเคยรัน `yarn dev` ทิ้ง type
  ไว้ที่ `.next/dev/types/` แล้ว (ไม่ commit เพราะอยู่ใน `.gitignore`) แต่ CI clone repo ใหม่ทุกครั้ง
  ถ้าไม่สร้าง type ก่อน `tsc --noEmit` แบบ standalone จะพัง TS2304 (`Cannot find name 'LayoutProps'`)
  — ถ้าจะรัน typecheck เองบนเครื่องที่ลบ `.next/` ไปแล้ว ให้รัน `npx next typegen` ก่อนเสมอ
- ยังไม่มี step build/push Docker image ใน CI — ยังไม่ได้กำหนด registry หรือ deploy target
  จึงยังปล่อยเป็น `docker build` แบบ manual ไปก่อน เพิ่มเมื่อทีมตัดสินใจปลายทาง deploy
